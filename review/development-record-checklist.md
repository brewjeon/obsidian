# 개발 기록 점검 기준

## 보여야 할 개발 흐름

이 프로젝트 기록은 단순한 클론 코딩 결과물이 아니라, 지역 기반 거래 서비스의 문제를 제품과 시스템 관점에서 나누고 꾸준히 검증한 과정을 보여야 한다.

기록에서 드러나야 하는 기준은 다음과 같다.

- 기능을 만들기 전에 실행 가능성과 검증 기준을 먼저 세운다.
- 작은 기능도 테스트, 실제 요청, 문서로 닫는다.
- 지역, 거래, 신뢰, 커뮤니케이션 같은 도메인 문제를 기술 구조와 연결해서 생각한다.
- 학습 기록을 남기는 데서 끝나지 않고, 다음 구현 판단에 재사용한다.

## Chapter 01에서 확인한 점

`/health` API는 작지만 중요한 시작점이다. 프로젝트가 실제로 뜨고 HTTP 요청에 응답한다는 사실을 먼저 확인했기 때문이다.

이 단계에서 확인한 점은 다음과 같다.

- 빌드 성공과 서버 실행을 구분했다.
- 자동화 테스트와 실제 HTTP 호출을 모두 수행했다.
- 백엔드와 프론트엔드 저장소의 역할을 최소한으로 나눴다.
- README를 작성해 실행 흐름을 따라올 수 있게 했다.

## Chapter 02에서 확인한 점

Docker Compose로 PostgreSQL과 PostGIS 환경을 구성하고, 파일을 작성한 것으로 끝내지 않고 설정 해석, 컨테이너 상태, DB 연결 준비, 실제 버전을 서로 다른 방법으로 확인했다.

이 단계에서 확인한 점은 다음과 같다.

- 이미지와 컨테이너, 프로세스 실행과 health 상태를 구분했다.
- 지역 기반 서비스라는 제품 특성을 PostGIS 선택과 연결했다.
- named volume으로 상태를 컨테이너 수명과 분리했다.
- `.env`와 `.env.example`의 공개 범위를 구분했다.
- 하나의 명령으로 모든 것을 확인했다고 주장하지 않고 검증별 보장 범위를 나눴다.

아직 보강해야 할 점은 다음과 같다.

- PostGIS를 실행했지만 실제 공간 타입, 거리 검색, 공간 인덱스는 사용하지 않았다.
- 기존 데이터 디렉터리 재사용은 확인했지만 특정 데이터 행의 보존을 전후 조회로 증명하지 않았다.
- JPA 설정 이후 실제 DB 연결과 Spring Context 로딩 검증이 필요하다.

구현하지 않은 내용을 확장해서 말하지 않고, 어디까지 검증했고 다음 위험은 무엇인지 정확히 남기는 편이 더 신뢰할 수 있는 기록이다.

## 앞으로 더 강하게 만들어야 할 기준

### 1. 기능보다 경계를 먼저 설명하기

예를 들어 게시글 기능을 만들 때 바로 CRUD로 들어가지 말고 다음을 먼저 정리한다.

- 게시글은 어떤 상태를 가지는가
- 판매자와 구매자는 어떻게 연결되는가
- 위치 정보는 어느 수준까지 저장하는가
- 삭제, 숨김, 거래 완료는 어떻게 다른가
- 검색과 피드는 어떤 기준으로 나뉘는가

### 2. 테스트 이름에 의도를 담기

나쁜 예:

```text
createPostTest
```

좋은 예:

```text
createsPostWhenRequiredFieldsAreValid
rejectsPostWhenPriceIsNegative
```

테스트 이름은 검증 의도를 드러내야 한다. 무엇을 검증했고 왜 중요한지 알 수 있어야 한다.

### 3. API를 문서처럼 설계하기

기능 구현 전에 최소한 다음을 적는다.

```http
POST /posts
Content-Type: application/json

{
  "title": "핸드드립 세트",
  "price": 25000,
  "description": "상태 좋습니다.",
  "regionId": 1
}
```

그리고 성공과 실패 응답을 같이 남긴다. 거래 서비스에서는 정상 흐름뿐 아니라 예외 흐름에서도 사용자 경험과 신뢰가 중요하다.

### 4. 회고는 감상이 아니라 다음 구현 기준으로 남기기

좋은 회고는 다음 질문에 답해야 한다.

- 이번 챕터의 구현이 다음 기능에 어떤 기반을 만들었는가
- 어떤 결정을 나중에 바꿀 수 있는가
- 지금은 단순하게 둔 이유가 무엇인가
- 다음에 검증해야 할 위험은 무엇인가

## 포트폴리오에 남길 문장 톤

`brew-market`을 단순 CRUD 프로젝트로 만들지 않고, 지역 기반 거래 서비스의 핵심 문제를 작게 쪼개 검증하는 방식으로 개발했다. Chapter 01에서는 도메인 기능보다 먼저 Spring Boot 애플리케이션이 HTTP 요청을 처리하는 기준선을 만들고, Controller 테스트와 실제 `curl` 호출로 서로 다른 검증 층을 확인했다.

## 계속 지켜야 할 원칙

- 각 챕터마다 하나 이상의 실행 가능한 결과물을 남긴다.
- 모든 기능은 테스트 또는 명확한 수동 검증 방법을 가진다.
- README는 현재 상태와 실행 방법이 항상 맞아야 한다.
- 중요한 기술 선택은 ADR로 남긴다.
- 기술 설명은 문서에서 외우는 것이 아니라 구현 경험에서 뽑아낸다.
- 실행 성공, 준비 상태, 기능 동작, 데이터 보존처럼 서로 다른 검증 수준을 구분한다.
- 비밀값이 추적 대상 파일에 들어가지 않았는지 커밋 전에 확인한다.
